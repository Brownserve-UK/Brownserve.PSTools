## Build System

The project uses [Invoke-Build](https://github.com/nightroman/Invoke-Build) via `.build/build.ps1`. All build tasks are defined in `.build/tasks/build_tasks.ps1`.

```powershell
# Build the module only
.\.build\build.ps1 -Tasks Build

# Build and import into the current session
.\.build\build.ps1 -Tasks BuildAndImport

# Build and run tests (most common during development)
.\.build\build.ps1 -Tasks BuildAndTest

# Build, test, and run all checks (what CI runs on PRs)
.\.build\build.ps1 -Tasks BuildTestAndCheck
```

Dependencies are managed via **Paket** (`paket.dependencies`). Run `.\.paket\paket.exe restore` to restore them into the `.tmp/` directory before building.

## Testing

Tests use **Pester** and live in `.build/tests/`:

- `Module.Tests.ps1` - Module import and cmdlet availability
- `Help.Tests.ps1` - Documentation completeness and structure
- `Common.Tests.ps1` - Utility cmdlet unit tests

To run a single test file:
```powershell
# Build first, then invoke Pester directly
.\.build\build.ps1 -Tasks Build
Invoke-Pester .\.build\tests\Common.Tests.ps1
```

## Architecture

### Module Loading

`Module/Brownserve.PSTools.psm1` is the entry point. It dot-sources all files from `Module/Private/` recursively, then exports all public functions from `Module/Public/` recursively. The module also creates a user config directory at `~/.brownserve/` and a global temp path variable (`$global:BrownserveTempLocation`).

### Public vs Private Functions

- `Module/Public/` - 96 exported cmdlets organized into subdirectories by domain
- `Module/Private/` - Internal helpers, not exported; same subdirectory naming convention

Each function lives in its own `.ps1` file named after the cmdlet (e.g., `Merge-Hashtable.ps1`).

### Public Cmdlet Domains

| Directory | Purpose |
|-----------|---------|
| `Build/` | Repo initialization, changelog management, versioning, release staging |
| `Common/` | General utilities: file I/O, assertions, content formatting, type conversion |
| `Git/` | Git operations: commits, branches, merges, repo cloning |
| `GitHub/` | GitHub API: PRs, releases, issues, asset uploads |
| `Terraform/` | Terraform init/plan/apply and validation helpers |
| `PowerShell/` | PS module scaffolding and PlatyPS documentation generation |
| `Teamcity/` | TeamCity CI/CD integration |
| `Vault/` | HashiCorp Vault secret retrieval |
| `Markdown/` | Markdown file manipulation |
| `Slack/` | Slack webhook notifications |

### Custom Classes

`BrownserveContent` (in `Module/Private/General/`) is a key class that wraps file content with line-ending awareness. It is used throughout the module when reading and writing files to ensure consistent line endings.

### Build Output

The build system outputs the complete module (manifest `.psd1`, `.psm1`, all functions) to `.tmp/output/Brownserve.PSTools/`. This directory is ephemeral and not committed.

### Module Manifest

The `.psd1` manifest is **generated** during the build from `.build/ModuleInfo.json` (name, GUID, tags, description). There is no static manifest in source control.

## Documentation

Cmdlet documentation is auto-generated by PlatyPS via the `BuildModuleDocumentation` cmdlet (part of the `PowerShell` domain) and stored in `Docs/Brownserve.PSTools/`. Each public cmdlet must have complete comment-based help for the `Help.Tests.ps1` tests to pass.

## Code Style

- Allman brace style (opening brace on its own line) for PowerShell code
- EditorConfig enforces indentation and line endings (`.editorconfig`)
- VS Code PowerShell extension auto-corrects aliases and pipeline indentation on save (`.vscode/settings.json`)
